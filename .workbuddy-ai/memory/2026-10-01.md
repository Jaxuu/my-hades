## 关键架构决策（后续改这里前必读）

1. **事件桥接 = `TeeEventQueue<T> extends EventQueue<T>` 覆写 `emit`**（先留客户端副本、再 `super.emit`），三个 tee 队列注入 `createDefaultSystems(hit, death, dash)`。**这是本里程碑最重要的发现**：`EventQueue` 的 `emit/drain/clear` 全是 public，所以「留存瞬时事件」根本不需要动 `src/` —— 比任务书设想的 `GameSimulator.onFrameEnd(events)` 更干净（后者要把一个**纯表现层概念**注入 `src/core`）。类型上完全 Liskov 兼容，管道仍只看到普通 `EventQueue`。
2. **客户端缓冲不受 `scheduler.reset()` 管辖**：`restartRun` 只会让 `DeathSystem`/`ModifierSystem` 清**它们自己的**总线，客户端缓冲不在调度器里 ⇒ 必须在 run 边界显式 `bridge.clear()`（`main.ts` 的 `onStartRun` 与 `onReload` 两处），否则会把引用「刚被销毁的实体」的事件重放到新一局。
3. **`drainFrame()` 每渲染帧恰好消费一次**：落在 `GameLoop.syncFrame(alpha)`，是 `renderer.syncWorld` 的**唯一**调用点（HUB 早退分支与正常分支都走它），所以既不会漏 drain 也不会重复 drain。一帧内最多 5 个逻辑 Tick 的事件会在缓冲里累积。
4. **粒子层走「惰性挂载」而非常驻节点**：`particleLayer` 只在「至少一个粒子存活」时挂进 `cameraContainer`（插在 `root` **之前**），清空即摘除。理由见下条——任何**常驻**新场景节点都会撞坏六条冻结契约之一。空闲态场景图与 M14 前**逐位相同** ⇒ 五个既有渲染套件**一行未改**。
5. **⚠️ 六条渲染场景图冻结契约**（M5/M12 遗留，改渲染前必查；测试里的 `renderRoot()` 助手写法是 `camera = stage.children[0]`、`root = camera.children[length-1]`）：
   - F1 `app.stage.children` 长度 1 且 `[0] === camera`
   - F2 `camera.children[last] === root`
   - F3 `root.children[last] === fxLayer`
   - F4 `root.children[0]` === 首个实体视图
   - F5 无墙时 `camera.children` 长度**恰为 1**（有墙时 2：`[0]`=静态层）
   - F6 空闲时 `fxLayer.children` 长度**恰为 0**

## 关键决策与发现

1. **⚠️ 本次最重要的方法：无损优化必须用「快照摘要」自证，不能只靠既有测试全绿。** 摘要 = `listEntities() × listComponents()` 拼串过 FNV-1a，同 seed 跑同一 601-Tick 脚本。**既有 634 例全绿并不足以证明无损**——我的第一版分离相位优化（`Float64Array` + `factions: Int32Array`）让**全部 634 例通过**，但摘要从 `2309042484` 变成 `2992069332`（174→198 实体）。**根因**：`Faction` 是**字符串枚举**，`Int32Array` 把 `'Player'`/`'Enemy'` 都转成 `0` ⇒ 同阵营判定全失效 ⇒ 玩家与敌人互相分离。改用**槽位对象**（`SeparationBody`，faction 保持 `Faction`）后摘要逐位复原。
   ⇒ **可复用纪律：`src/` 的「无损」类改动，先取基线摘要，改完再取一次，两者必须相同；不一致就说明测试覆盖有洞。**
2. **性能归因靠插桩，不靠猜**：给 `world.query` / `world.getComponent` 打实例级包装，实测出 **每 Tick 42,122 次 `getComponent`**，其中 **`separateBodies` 双循环独占 ~34k**（每对 6 次、每次 2 次 `Map` 查找）。这才是真正的 O(N²) —— 不是「遍历次数多」，而是**每次遍历都在查表**。
3. **系统消融实验在本仓库不可用**：移除任一系统都会改变模拟轨迹（去掉 `EncounterSystem` ⇒ 根本不刷怪，总时长从 920ms 掉到 11ms），边际成本出现**负值**。归因只能靠**插桩计数**，不能靠消融。
4. **性能断言的守卫是「缩放比」而非「绝对预算」**：绝对墙钟随 CI 负载漂 2 倍（单跑 457ms / 全量并发 856ms）。故吞吐预算放宽到 2000ms，O(N²) 交给 `time(300敌)/time(50敌) < 9`。
   **变异实验**（临时 `git show HEAD:src/...MovementSystem.ts` 换回 M15 前实现，跑完备份还原，**未用 `git checkout --`**）：缩放比 **18.98** ⇒ 测试**失败**；吞吐 1137ms ⇒ 仍过（< 2000）。**证明缩放守卫是真正起作用的那条断言**，而吞吐断言只是兜底。
5. **100ms 为什么达不到（量化）**：优化后每 Tick 仍有 ~26 次 `World.query`（每次遍历全部 `alive`）+ ~5.5k 次 `World.getComponent`（每次 2 次 `Map` 查找）——这是 17 段管道 × ~174 实体的**固定每实体开销**。**测过极端下限**：150 个**完全惰性**（无 AI、不攻击）的 `grunt` 也要 ~460ms，说明与战斗无关。要压到 100ms 必须重写 `World` 组件存储 + 改写每个系统的读取方式 ⇒ **改的是核心逻辑与测试契约**，超出边界。
6. **空间网格被否决（有量化理由）**：数组/槽位化后分离相位 ~10ns/对，n≈150 时 ~11k 对/Tick；而网格需每体 9 次邻域查找（~150ns）+ 候选排序。更关键的是**等价性**：该 pass 是**就地松弛**（位置逐对更新，后面的对读的是已修正的位置），网格要求「位置在本 pass 内不变」⇒ 保逐位等价必须增量重建网格，复杂度远超收益。**结论：主导项已被槽位化清零（1187ms → ~65ms），网格在 n≈150 时反而更慢。**
7. **`World.query` 去 `sort` 是安全的（有契约依据）**：`alive` 是 `Set`，`createEntity` 是**唯一**写入者且 id 单调递增，`destroyEntity` 只删不改序，`clearEntities` 不重置计数器 ⇒ 迭代序**已升序**，`sort` 是对已排序数组的纯浪费（微基准实测 ~4.7µs/次稠密查询）。契约「升序」由 `tests/harness/ecs.test.ts` 钉住，**不变**。
8. **`GameRenderer.retired` 是真实泄漏（本里程碑发现并修复）**：它是渲染器**唯一无界**结构（`EntityId` 永不复用 ⇒ 只增不减），而 `restartRun` **不**释放它——只有 `renderer.reset()` 会。生产路径 `onStartRun` 原本只调 `restartRun` + `bridge.clear()` ⇒ 跨局累积。已补 `renderer.reset()`（run 边界调它是安全的：重开已销毁上一局全部实体，不存在「忘了 id 导致尸体复活」）。新增 `retiredCount` getter 供断言，并用「**不调 reset 则 `retiredCount > 0`**」的用例**显式证明泄漏存在、reset 是修复**（而不是只断言 reset 后为 0 —— 那是恒真断言陷阱的变体）。
9. **⚠️ node 侧测试不得 import `GameLoop`**：其构造参数具名 `KeyboardInput`（唯一合法使用裸 `window`/`Window`/`KeyboardEvent` 的 client 模块），会把 DOM 类型拖进**无 DOM 的根 tsconfig** 并报 **TS2304**。渲染泄漏测试因此改为断言「渲染器**从不**向 ticker 注册回调」（`renderer.ticker` 是 app ticker；`reset()` 没有能力注销别人的注册）。**这是 M5/M12 遗留约束的又一处体现。**
10. **`noUncheckedIndexedAccess` 对 typed array 也生效**：`Float64Array[i]` 是 `number | undefined`，`!` 被禁 ⇒ 要么每读一次加 `?? 0`（热循环里 3 次/对），要么改结构。**选了后者**（槽位对象：每对只需 1 次 `undefined` 守卫），顺带让语义更接近原实现（位置就地改写，无写回步骤）。
11. **数据驱动的边界**：`encounters.json` 是**按 depth 索引的序列**，`spawnFromData` 读**全部** depth ⇒ 新增 `depth: 2` 会让**正常 run 变成 3 间房**（第 3 间即 150 敌压测房）。这是数据模型的直接后果，已登记为取舍 T2，`?mode=stress` 是其唯一正当入口。**若要避免，只能改数据模型（超出「契约不改」的边界）。**
12. **`gunner` 是「会射击的精英怪」在本引擎的唯一合法形态**：`armor:40` + `ai.attackRadius:12` + `hazard`（站在 12 单位外朝玩家掷延迟 AoE）。**不新增任何 AI 能力**（`IntentComponent.wantsToCast` 仍只由玩家硬件驱动）——加「敌人会射弹」属于改核心逻辑，被边界排除。

## 踩到的坑

- **`noUncheckedIndexedAccess` 让 typed-array 方案必须先过类型关**：我先写了 `Float64Array` 版（微基准 65ms，最快），但 `tsc` 报 12 处 `possibly undefined`；`!` 被禁、`?? 0` 会在热循环里加 3 次/对的判空。**改结构（槽位对象）比硬加判空更干净**，且性能同量级。
- **性能测试的阈值不能照抄任务书**：任务书写 100ms，实测 460ms。**如实登记 + 用「缩放比」做真正的回归守卫**，比把阈值改成能过更有价值。
- **第一次写 `render_leak.test.ts` 时 `retiredCount` 恒为 0**（用例失败）：因为 `applyDamage` 只改 `hp`，**死亡标签是 `DeathSystem` 在 Tick 末写的**，而我没 `step()` ⇒ 渲染器看不到死亡、不播 FX、不 retire。**教训：断言「某状态出现」前，先确认**产生**该状态的系统真的跑过。**
