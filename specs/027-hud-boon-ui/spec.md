# Feature Specification: UI 层重构：材质化 HUD 与祝福交互面板（M19）

**Feature Branch**: `027-hud-boon-ui`

**Created**: 2026-10-03

**Status**: Draft

**Input**: User description: "彻底重构游戏的 UI 层（M19）。在表现层引入具有美术质感的 HUD 和局内“祝福（Boon）”交互面板。要求：1. 将简陋的血条、冲刺充能、金币数值替换为带有材质感的高清 UI 组件；2. 房间清理完毕后，弹出精美的“三选一”祝福卡片面板，卡片必须包含品质颜色区分（蓝/紫/金）、对应图标以及清晰的数值化效果描述（例如“冲刺时在原地引发 30 点雷电伤害”）；3. 增加一个局内状态面板（例如按 Tab 键呼出），陈列玩家当前拥有的所有祝福及其描述；4. UI 层的交互和渲染必须通过严格的事件总线或状态探针进行，绝对禁止反向污染核心逻辑层（src/）；5. 确保现有的 948 个测试用例保持 100% 通过。"

**三项用户裁定（2026-10-03）**：

1. **品质机制 = 静态品质**：每个祝福在数据表中声明一个硬编码的 `rarity` 字段（Common=蓝 / Epic=紫 / Legendary=金），UI 只读该字段渲染对应颜色。**严禁修改 `src/` 核心层的随机掉落算法，严禁在运行时动态生成或抽取品质**，品质不改变任何数值。
2. **局内状态面板 = 不暂停**：Tab 面板为纯覆盖层，打开时模拟照常推进。
3. **交付边界 = 含既有覆盖层**：死亡 / 胜利 / 营地三个既有覆盖层一并纳入统一的 HD UI 视觉语言。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 局内 HUD 升级为材质化高清组件 (Priority: P1)

玩家在战斗全程看到的生命、冲刺充能、金币不再是角落里的几行等宽文本，而是三件有材质、有质感、一眼可读的 HUD 组件：生命是一条带材质底纹的条（同时给出数值与比例），冲刺充能是一个能读出「能不能冲、还有多久冷却好」的图形指示，金币是一块带底纹的读数牌。玩家无需把视线从战斗中心移开，就能判断「我还剩多少血、能不能闪、这把赚了多少」。

**Why this priority**: HUD 是屏幕上出现时间最长、刷新最频繁的表面，也是用户第一条要求（「将简陋的血条、冲刺充能、金币数值替换为…」）的直接对象。它是「这次重构有没有发生」的第一判断标准，缺少它本特性没有可交付价值。

**Independent Test**: 只实现本故事即可交付：进入一局游戏，分别让玩家受伤、冲刺、拾取金币，观察三件 HUD 组件是否随之实时、正确地变化，且不再以纯文本形式呈现血条读数。无需祝福卡片或 Tab 面板即可完整验证。

**Acceptance Scenarios**:

1. **Given** 玩家满血进入房间，**When** 玩家受到伤害，**Then** 生命组件同步更新其数值与比例，读数与真实生命一致。
2. **Given** 冲刺处于冷却中，**When** 玩家观察冲刺组件，**Then** 组件明确表达「冷却中」及其进度；冷却结束后明确表达「可用」。
3. **Given** 玩家拾取金币，**When** 钱包增加，**Then** 金币组件同步显示当前这一局的金币数。
4. **Given** 屏幕上同时存在 HUD 与任意覆盖层（三选一 / 死亡 / 胜利 / 营地），**When** 观察 HUD，**Then** HUD 仍然正确、未被覆盖层破坏。
5. **Given** HUD 读数在一帧内没有变化，**When** 画面刷新，**Then** HUD 不出现可见闪烁或抖动。

---

### User Story 2 - 房间清理后的三选一祝福卡片 (Priority: P1)

清空一间房间后，玩家面对的不再是三个只有英文名的纯文字按钮，而是三张精美的祝福卡片：每张卡片有明确的品质颜色（蓝 / 紫 / 金）边框、专属图标，以及一句把效果讲清楚的数值化描述——例如「攻击命中时在目标处引发 20 点雷电伤害」「冲刺时在原地引发冲击波，造成 5 点伤害并击退 40」。玩家能在一秒内分辨出「哪张更强（品质）、这张是干什么的（图标 + 描述）、具体有多强（数值）」。

**Why this priority**: 三选一是肉鸽循环里最核心的决策瞬间，也是用户第二条要求。它直接决定「玩家能不能看懂自己在选什么」——没有品质、图标与数值描述，选择就退化为盲选。

**Independent Test**: 只实现本故事即可交付：清空任意一间房间，观察弹出的三张卡片是否各自带有品质颜色、图标与数值化描述，且描述中的数值与逻辑层的真实效果一致。

**Acceptance Scenarios**:

1. **Given** 房间被清理，**When** 三选一面板弹出，**Then** 面板呈现恰好三张可选择的祝福卡片（沿用既有抽取结果，不改触发与数量）。
2. **Given** 一张卡片，**When** 玩家观察，**Then** 卡片同时具备品质颜色、图标与数值化描述三要素。
3. **Given** 两个不同品质的祝福同屏，**When** 玩家观察，**Then** 仅凭边框颜色（蓝/紫/金）即可区分二者品质。
4. **Given** 一张描述为「造成 N 点伤害」的卡片，**When** 与逻辑层的真实数值核对，**Then** N 与真实数值完全一致。
5. **Given** 玩家点击一张卡片，**When** 选择发生，**Then** 通过既有交互契约（`onSelect(id)` → 选择输入）授予该祝福，UI 不越权直接修改世界。

### User Story 3 - 按 Tab 呼出的局内状态面板 (Priority: P1)

玩家在局内按 Tab 可以随时呼出一块状态面板，上面陈列当前已经拥有的全部祝福及其描述（含品质与图标），像一份随身的「能力清单」。面板打开时游戏照常推进，不会因为「翻看清单」而暂停战斗——它只是一层覆盖在画面上的参考信息。

**Why this priority**: 用户第三条要求。随着祝福累积，玩家需要一个随时可查的汇总入口，否则「我现在到底带了什么」只能靠记忆。它同样验证了「表现层可读、但不干预模拟」这一核心约束。

**Independent Test**: 只实现本故事即可交付：先通过任意方式让玩家拥有若干祝福，再按 Tab，观察面板是否列出全部已拥有祝福及其描述；再次按 Tab 收起。无需 HUD 或卡片即可验证。

**Acceptance Scenarios**:

1. **Given** 玩家拥有若干祝福，**When** 按下 Tab，**Then** 面板呼出并陈列全部已拥有祝福及其描述。
2. **Given** 面板已打开，**When** 玩家再次按下 Tab，**Then** 面板收起。
3. **Given** 面板已打开，**When** 对比「面板打开」与「面板关闭」两条相同输入的模拟轨迹，**Then** 二者的逐 Tick 状态完全一致（面板未改变模拟）。
4. **Given** 玩家尚未拥有任何祝福，**When** 按下 Tab，**Then** 面板给出明确的「暂无祝福」空状态，而非空白或报错。
5. **Given** 玩家拥有大量祝福，**When** 面板呼出，**Then** 列表可滚动查看，不溢出、不遮挡到无法操作。

---

### User Story 4 - 纯表现层：零污染、零回归 (Priority: P1)

无论界面变得多么精美，游戏的玩法与逻辑完全不变：本次重构只改变「看起来是什么样」，绝不改变「实际是什么」。UI 的每一次读取都经过只读探针或事件总线，逻辑内核（`src/`）一个文件都不改，既有的 948 个测试用例全部保持绿灯。

**Why this priority**: 这是用户明确写下的硬约束（要求 4 与要求 5），也是项目的安全底线。一旦被违反，整个确定性保证与 948 例回归基线即刻作废。它必须与前三条 P1 故事同时成立，而不是事后补票。

**Independent Test**: 只实现本故事即可交付：在固定种子与固定输入序列下，分别以「改动前」与「改动后」运行同一段模拟，比较两次的状态序列与快照摘要；并检查改动后的源码差异中 `src/` 的文件数为零。

**Acceptance Scenarios**:

1. **Given** 相同的种子与相同的输入序列，**When** 分别在改动前与改动后运行模拟，**Then** 两次产生的状态逐 Tick 完全一致（差异处数 = 0），且快照摘要逐位相同。
2. **Given** 全部 UI 改动就位，**When** 检查依赖方向，**Then** 不存在任何从逻辑内核指向表现层的依赖；逻辑内核的改动文件数为 0。
3. **Given** 全部 UI 改动就位，**When** 检查掉落 / 抽取逻辑，**Then** 掉落算法与抽取结果与改动前一致，品质未参与任何随机或数值计算。
4. **Given** 全部 UI 改动就位，**When** 运行完整测试套件，**Then** 既有测试 100% 通过，且逐 Tick 管道仍为既有段数与顺序。

---

### User Story 5 - 既有覆盖层纳入统一 HD 视觉语言 (Priority: P2)

死亡、胜利、营地三个既有全屏界面不再停留在「旧皮肤 + 新 HUD」的割裂状态，而是与本特性的 HUD、祝福卡片共用同一套 HD UI 视觉语言（同一材质、同一品质色系、同一排版基调）。玩家在「打斗 → 三选一 → 死亡 → 回营地」的完整循环里，感受到的是一以贯之的界面质感，而不是两代界面的拼接。

**Why this priority**: 用户第三项裁定明确要求覆盖层纳入统一视觉。它属于「彻底重构 UI 层」的完整性要求，但不是前三条 P1 故事的可玩性前提——即使覆盖层保持原样，HUD / 卡片 / 面板也已构成完整交付。定为 P2 是因为它提升的是整体一致性而非新增能力。

**Independent Test**: 只实现本故事即可交付：分别触发死亡、胜利与营地界面，观察三者是否与本特性的 HUD 与卡片在材质、配色、排版上风格统一，且各自的既有功能（R 回营地、购买天赋、开始逃离）仍然可用。

**Acceptance Scenarios**:

1. **Given** 一局失败，**When** 死亡覆盖层出现，**Then** 其视觉与本特性的 HUD / 卡片属于同一 HD 语言，且「按 R 回营地」仍然可用。
2. **Given** 一局胜利，**When** 胜利覆盖层出现，**Then** 其视觉与死亡覆盖层同属一套语言但可明显区分（正负两极），且行为一致。
3. **Given** 玩家位于营地，**When** 营地界面出现，**Then** 其视觉与全站统一，且天赋购买与「开始逃离」交互契约不变。

---

### User Story 6 - 优雅降级、文本可读与键盘可达 (Priority: P2)

界面再漂亮，也不能在资产出问题时崩溃或变瞎：当某个 UI 资产缺失或解码失败时，界面回退到朴素的纯样式表现并照常可用；中文文本在任何机器上都渲染为字形而非「豆腐块」，且不依赖任何需要下载的网络字体；所有可交互元素都能用键盘聚焦，焦点清晰可见。

**Why this priority**: 这是交付质量的底线而非新体验，优先级低于前几条；但它必须在任何一次合并前成立，否则「高清 UI」会在弱环境或无障碍场景下反噬可用性。

**Independent Test**: 只实现本故事即可交付：人为移除/损坏一个 UI 资产，观察界面是否仍可用；检查样式表中不含网络字体声明且含中文字体回退；用键盘 Tab 遍历全部可交互元素，确认焦点环可见。

**Acceptance Scenarios**:

1. **Given** 某个 UI 资产缺失或解码失败，**When** 界面渲染，**Then** 该表面回退到纯样式表现，游戏照常可用，不崩溃、不黑屏。
2. **Given** 中文界面文本，**When** 在无该字体的机器上渲染，**Then** 文本显示为字形而非方框，且不发起任何网络字体请求。
3. **Given** 玩家仅使用键盘，**When** 逐次按 Tab 遍历界面，**Then** 每个可交互元素都能获得焦点，且焦点环清晰可见。

---

### Edge Cases

- 当某个祝福在数据表中**未声明**品质 / 图标 / 描述时，卡片如何表现？（必须回退到默认品质外观与占位图标/描述，而非空白或崩溃）
- 当数据表声明的祝福 id 与逻辑层祝福目录**不一致**（悬空 id 或缺失 id）时，如何表现？（必须降级而非崩溃，且不得影响抽取结果）
- 当描述模板缺少所需数值（例如逻辑层数据未覆盖该祝福）时，如何表现？（必须给出不含数值的安全描述，而非显示 `undefined` / `NaN`）
- 当玩家生命为 `0`（濒死）或 `maxHp` 为 `0` 时，生命条如何表现？（不得出现除零或反向条）
- 当冲刺冷却恰好为 `0` / 恰好为满冷却时，冲刺组件如何表现？（可用 / 冷却中边界清晰）
- 当金币数值极大（数千）时，金币牌如何表现？（不溢出、不截断到不可读）
- 当玩家在**三选一面板打开期间**按下 Tab 时，两个覆盖层如何互斥？（不得同时呈现冲突内容）
- 当玩家在**死亡/胜利/营地**状态下按下 Tab 时，面板如何表现？（不得破坏终局界面或残留监听）
- 当玩家拥有**零个**或**极大量**祝福时，Tab 面板如何表现？（空状态明确；大量时可滚动）
- 当祝福在一帧内被授予、玩家同帧按 Tab 时，面板内容是否与实际拥有集合一致？
- 当同一品质的多个祝福同屏时，卡片是否仍可互相区分（图标/名称）？
- 当 UI 资产文件被删除或损坏时，构建是否响亮失败 / 运行期是否优雅降级？
- 当显示倍率非整数或视口尺寸变化时，材质化组件是否出现拉伸、错位或模糊？
- 当色觉障碍玩家观看蓝/紫/金卡片时，是否仍有颜色以外的区分线索？（品质纹理/图标/文字标签）

## Requirements *(mandatory)*

### Functional Requirements

#### A. 材质化 HUD（生命 / 冲刺充能 / 金币）

- **FR-001**: 局内 HUD MUST 以**材质化图形组件**呈现生命值、冲刺充能、金币三项读数，取代当前的纯文本读数。
- **FR-002**: 生命组件 MUST 同时以「数值 + 比例」两种方式表达当前值与上限值，并 MUST 随生命变化实时更新。
- **FR-003**: 冲刺组件 MUST 明确表达「可用 / 冷却中」状态及其冷却进度；其数据 MUST 派生自逻辑层公布的冲刺状态（只读）。
- **FR-004**: 金币组件 MUST 显示当前这一局的金币数（只读派生自逻辑层的钱包读数）。
- **FR-005**: HUD MUST 为**常驻**表面：无论当前是否显示任何覆盖层，HUD MUST 保持正确。
- **FR-006**: HUD 的刷新 MUST 在读数未变化时保持无副作用：该帧 MUST NOT 重建或改写任何 HUD 节点（**以「DOM 写入次数 = 0」判定**，取代不可测的「无可见闪烁」表述）。
- **FR-007**: 既有诊断信息块与新 HUD MUST 明确分离，MUST NOT 产生重复或互相矛盾的读数。

#### B. 三选一祝福卡片面板

- **FR-010**: 房间清理完毕后 MUST 弹出三选一面板；其**触发条件、弹出时机与选项数量 MUST 沿用既有行为**，MUST NOT 新增或改变。
- **FR-011**: 每张卡片 MUST 展示**品质颜色**（蓝 / 紫 / 金）；颜色 MUST 由数据表中该祝福声明的 `rarity` 字段决定。
- **FR-012**: 每张卡片 MUST 展示该祝福的**图标**。
- **FR-013**: 每张卡片 MUST 展示一句**数值化效果描述**，其中 MUST 包含该祝福的真实数值（如「攻击命中时在目标处引发 20 点雷电伤害」）。
- **FR-014**: 描述中的数值 MUST 与逻辑层的真实数值一致；MUST NOT 维护第二份可能与逻辑层漂移的数值来源。
- **FR-015**: 卡片的交互契约 MUST 保持不变：点击卡片 MUST 经既有回调（`onSelect(id)`）转化为选择输入；UI MUST NOT 直接授予祝福或写世界。
- **FR-016**: 品质 MUST **纯粹是外观**：MUST NOT 改变任何数值、掉落概率或抽取结果。
- **FR-017**: 当某祝福的图标 / 描述 / 品质未声明时，卡片 MUST 优雅降级（默认品质外观 + 占位图标/安全描述），MUST NOT 空白或崩溃。

#### C. 局内状态面板（Tab）

- **FR-020**: 玩家 MUST 能通过按 Tab 呼出与收起局内状态面板。
- **FR-021**: 面板 MUST 陈列玩家**当前拥有的全部祝福**及其描述（含品质与图标）。
- **FR-022**: 面板 MUST NOT 暂停、推进或改变模拟；打开面板 MUST NOT 使模拟轨迹与关闭时产生任何差异。
- **FR-023**: 面板内容 MUST 与玩家实际拥有的祝福集合保持实时一致。
- **FR-024**: 面板 MUST 正确处理**空集合**（明确的空状态）与**大量祝福**（可滚动、不溢出、不遮挡操作）。
- **FR-025**: Tab 键监听的生命周期 MUST 严格受控：仅在局内激活；进入终局 / 营地或销毁后 MUST NOT 残留任何监听。
- **FR-026**: 面板与既有覆盖层（三选一 / 死亡 / 胜利 / 营地）MUST 互斥且具有明确的优先级，MUST NOT 同时呈现相互冲突的内容。

#### D. 纯表现层与数据驱动（硬约束）

- **FR-030**: 本特性的全部改动 MUST 只发生在表现层（`client/`、UI 资产与表现层数据表）；逻辑内核（`src/`）的改动文件数 MUST 为 0。
- **FR-031**: MUST NOT 修改 `src/` 的掉落 / 抽取算法；品质 MUST NOT 在运行时被生成、抽取或计算。
- **FR-032**: 依赖方向 MUST 保持单向（表现层 → 逻辑内核）；MUST NOT 引入任何从逻辑内核指向表现层的依赖。
- **FR-033**: UI MUST 仅通过**只读探针或事件总线**读取逻辑层；MUST NOT 调用任何写 API、MUST NOT 推进模拟、MUST NOT 修改 `World`。
- **FR-034**: 品质、图标与描述 MUST 来自**声明式数据表**，MUST NOT 硬编码在渲染分支中。
- **FR-035**: 数据表 MUST 覆盖全部可抽取的祝福；其 id MUST 与逻辑层的祝福目录保持一致；出现悬空或缺失 id 时 MUST 降级而非崩溃。
- **FR-036**: 新增的表现层数据表 MUST NOT 改变 `src/` 的数据加载与校验行为（逻辑内核只加载其既有的具名数据表）。

#### E. 既有覆盖层统一 HD 视觉语言

- **FR-040**: 死亡、胜利、营地三个既有覆盖层 MUST 纳入与本特性 HUD / 卡片统一的 HD UI 视觉语言。
- **FR-041**: 覆盖层的**既有语义与交互契约 MUST NOT 改变**（R 回营地、天赋购买、开始逃离、终局的优先级）。
- **FR-042**: 既有的冻结 class 钩子与元素 id MUST 保留；若因重构必须变更，MUST 在本规格中显式登记，MUST NOT 隐性破坏既有 UI 契约测试。

#### F. 降级 / 可读性 / 可达性 / 预算 / 回归

- **FR-050**: 运行期 UI 资产缺失、损坏或解码失败时，系统 MUST 优雅降级（回退到纯样式表现），MUST NOT 崩溃、黑屏或阻塞游戏循环。
- **FR-051**: 界面文本 MUST 保持可读：中文 MUST 渲染为字形而非方框，且 MUST NOT 依赖任何需要下载的网络字体。
- **FR-052**: 键盘可达性 MUST 保持：全部可交互 UI 元素 MUST 可被键盘聚焦，且焦点环 MUST 可见。
- **FR-053**: 新增 UI 资产 MUST 随应用本地分发（外部请求数 = 0），并 MUST 满足**既有的全局资产体积预算**（单文件 ≤ 3 MiB / 总量 ≤ 12 MiB）；本特性**不另设**更紧的 UI 子预算。
- **FR-054**: 既有渲染场景图的冻结契约 MUST NOT 被破坏；若新增常驻节点，MUST 采用惰性挂载或为契约补充显式同步钉桩，MUST NOT 放宽或删除既有断言。
- **FR-055**: 既有 948 个测试用例 MUST 100% 通过（失败 0）；与 UI 皮肤 / 资产结构耦合的测试（`tests/ui/*`）MAY 随本特性更新，**更新后总数 MUST NOT 低于 948**。
- **FR-056**: 表现层性能 MUST 以**比值口径**验收（同机、同场景、同一脚本下，改动后 / 改动前的每帧耗时中位数 ≤ 1.2），MUST NOT 使用绝对墙钟阈值。

### Key Entities *(include if feature involves data)*

- **祝福（Boon / Reward）**：可被抽取并授予玩家的能力单元。关键属性：`id`、显示名、**品质**、图标、数值化描述、真实效果数值（只读派生自逻辑层）。
- **品质（Rarity）**：三级 —— `Common`（蓝）/ `Epic`（紫）/ `Legendary`（金）。仅决定卡片外观，不参与任何数值或随机。
- **祝福数据表（表现层）**：一份声明式的祝福元数据表（如 `boons.json`），逐条记录 `id → { rarity, icon, description }`；由表现层只读，逻辑内核不感知其存在。
- **HUD 组件**：生命、冲刺充能、金币三件常驻只读组件，分别派生自逻辑层的生命、冲刺与钱包读数。
- **局内状态面板**：Tab 呼出的只读汇总表面，内容 = 玩家当前拥有的祝福集合。
- **只读探针 / 事件总线**：表现层观察逻辑层的唯一通道（既有只读访问器 + 客户端事件桥），本特性 MUST 沿用并仅沿用该通道。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在受伤 / 冲刺 / 拾取金币三种情形下，观察者能在 1 秒内正确读出生命、冲刺状态与金币数，正确率 100%；且血条 / 冲刺 / 金币不再以纯文本形式呈现。
- **SC-002**: 三选一面板中，每张卡片同时携带「品质颜色 + 图标 + 数值化描述」三要素的比例 = 100%（逐卡核验）。
- **SC-003**: 卡片品质颜色与数据表声明一致的比例 = 100%，且蓝 / 紫 / 金三色两两可区分。
- **SC-004**: 全部祝福的数值化描述中的数值与逻辑层真实数值的一致率 = 100%（逐祝福核验）。
- **SC-005**: Tab 面板列出的祝福集合与玩家实际拥有集合的一致率 = 100%。
- **SC-006**: 在固定种子与固定输入下，「面板打开」与「面板关闭」两条轨迹的模拟状态逐 Tick 一致（差异处数 = 0）。
- **SC-007**: 逻辑内核（`src/`）的改动文件数 = 0（以源码差异实测）；反向依赖（逻辑内核 → 表现层）的引用数 = 0。
- **SC-008**: 在固定种子与固定输入序列下，改动前后的模拟状态逐 Tick 完全一致（差异处数 = 0），且快照摘要逐位相同。
- **SC-009**: 既有测试 100% 通过（失败 0），且改动后全部测试用例总数 ≥ 948。
- **SC-010**: 人为缺失 / 损坏任意一个 UI 资产时，游戏可用率 = 100%（崩溃 0 次、黑屏 0 次）。
- **SC-011**: 中文界面文本在无对应字体的环境下渲染为字形的比例 = 100%（无方框），且网络字体请求数 = 0、外部请求数 = 0。
- **SC-012**: 既有渲染场景图的冻结契约在未修改其断言的前提下全部成立（成立率 = 100%）。
- **SC-013**: 在约 150 个敌人同屏的压测场景下，表现层每帧耗时中位数的「改动后 / 改动前」比值 ≤ 1.2（同机、同场景、连续 3 次取中位数）。
- **SC-014**: 观察者仅凭卡片外观区分蓝 / 紫 / 金品质的正确率 ≥ 90%。
- **SC-015**: 全部可交互 UI 元素的键盘可达率 = 100%（可聚焦且焦点环可见）。
- **SC-016**: 新增 UI 资产不超过**既有的全局体积预算**（单文件 ≤ 3 MiB / 总量 ≤ 12 MiB），以构建产物实测为准；本特性**不设**更紧的 UI 子预算。

## Assumptions

- **既有 UI 基座被沿用而非推翻**：本特性建立在 M16 已交付的 `--ui-*` 皮肤机制与 `index.html` 结构之上，在其上增强 / 替换为 HD 组件；不重写 `UIManager` 的既有分支语义（仅扩展）。
- **三项用户裁定作为既定输入**：品质为静态、声明式、纯外观；局内状态面板非阻塞；死亡 / 胜利 / 营地覆盖层纳入统一视觉。
- **祝福目录的现状（关键事实澄清）**：当前代码库**不存在** `boons.json`。可抽取祝福目录位于逻辑内核的 `src/ecs/rewards/RewardPool.ts`（5 条：`zeus_strike`、`dionysus_strike`、`poseidon_dash`、`hp_up`、`dash_up`），而 `assets/data/modifiers.json` 仅覆盖其中 2 条。因此用户所述「在现有数据表新增 `rarity` 字段」在实现上等价于**新增一份表现层可读的祝福数据表**（如 `boons.json`），承载 `rarity` / 图标 / 描述；其**具体路径与读取方式在规划阶段裁定**，硬约束是「`src/` 零改动」。
- **新增数据表对逻辑内核惰性**：`src/data/bundled.ts` 以**具名 import** 加载各数据表，故新增一份数据表不会被逻辑内核加载或校验，天然满足 FR-036 / FR-030。
- **数值化描述的数值来源**：优先**只读派生**自逻辑层（`assets/data/modifiers.json` 经 `DataManager`、或逻辑内核导出的常量）；数据表只承载「文案模板 + 缺口补齐」，且 MUST NOT 与逻辑层数值冲突（FR-014 / SC-004）。
- **品质为纯外观**：品质不参与数值、掉落概率与抽取结果；将其纳入任何随机或数值计算都违反 FR-016 / FR-031。
- **沿用既有约束**：M17 的相机缩放与视口语义、M18 的资产许可与体积约束、M16 的降级与文本可读性契约、以及宪法 Principle V（表现层隔离）与 Principle VI（既有核心不可重构）。
- **逻辑内核视为冻结资产**：本特性只在表现层做「状态 / 事件 → HD UI」的映射，不修改任何玩法规则或物理参数。
- **既有 UI 契约测试的处置**：`tests/ui/ui_skin.test.ts` 冻结了 class 钩子与元素 id，`tests/ui/text_readability.test.ts` 冻结了「无网络字体 + 中文回退」；本特性 MAY 扩展这两个套件（新增断言），但若需**改动**其既有断言，MUST 在本规格中显式登记（FR-042 / FR-055），且 948 例为**下限**。
- **已知风险（须在规划阶段给出缓解）**：
  - **描述漂移风险**：数值化描述中的数值若在表现层被复制，会与逻辑层真实数值漂移。缓解：单一来源 / 只读派生 + 交叉校验（SC-004）。
  - **体积预算风险**：新增 HD UI 组件资产可能挤压既有资产预算。缓解：**沿用既有全局预算**（单文件 ≤ 3 MiB / 总量 ≤ 12 MiB，本特性不另设子预算）并以构建产物实测（FR-053 / SC-016）。
  - **品质可辨性风险**：仅靠颜色区分品质对色觉障碍玩家不友好。缓解：颜色 + 图标 / 纹理 / 文字标签的多通道编码（Edge Cases 末条）。
  - **冻结钩子风险**：重构易在无意中改名或删除被 `tests/ui/ui_skin.test.ts` 冻结的钩子。缓解：先以契约测试锁定，任何变更显式登记。
