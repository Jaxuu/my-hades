## A. 视觉身份与风格锚点

### A.1 风格宣言（一句话）

> **「以暖光下的石质地牢为舞台，用高对比的剪影与清晰的顶面/立面分层，把希腊神话式的英雄与怪物画成一眼可读的战术棋子。」**

观感方向对齐《哈迪斯》的「俯视 · 明快 · 高可读」气质，但**全部资产为开放许可或本仓库原创 / 程序化生成**，与任何商业作品无资产级关联（FR-023）。

### A.2 视觉支柱（5 条）

| # | 支柱 | 具体规则 |
|---|---|---|
| V1 | **剪影优先（Silhouette First）** | 每个角色 / 敌人在**纯黑填充**下即可区分。外形轮廓必须承载身份信息，颜色只是加成（直接服务 FR-004 / SC-002「关闭颜色线索仍可区分」）。 |
| V2 | **暖角色 / 冷环境（Warm-Cool Split）** | 角色与敌人用**暖色相**（橙 / 红 / 金 / 苔绿偏暖），环境用**冷色相**（青灰石 / 沙色地面偏中性冷）。角色永远从地面里「跳」出来。 |
| V3 | **明度阶梯（Value Ladder）** | 同屏三层明度：**地面 ≤ 45%**（暗）、**墙体 45–65%**（中）、**角色 / 敌人 / 特效 ≥ 65%**（亮）。任何时刻，可交互物的明度 MUST 高于它所在的地面。 |
| V4 | **形态语言绑定职能（Shape = Role）** | 敌人外形编码其战斗职能：近战=厚重矮块、精英=高大带角、突袭=瘦长前倾、自爆=球形带引信、远程=悬浮带杖。玩家=标准直立人形（唯一「人」形基准）。 |
| V5 | **顶面 / 立面分层（Cap-Face Depth）** | 墙体用「顶面 + 立面 + 墙脚阴影」三带表达高度；三带**全部落在墙格自身 1×1 像素范围内**，永不外溢（保证 FR-008 / FR-010）。 |

### A.3 题材锚点

- **题材**：希腊神话 · 俯视动作肉鸽。
- **舞台**：石质地牢 / 神庙回廊（大理石柱、青铜纹样、马赛克地面）。
- **角色基调**：英雄（披风 + 护腕 + 短兵器）、怪物（斯巴达式护甲的精英、影化突袭者、熔火自爆者、悬浮祭司）。
- **合法性**：不采用任何商业作品的名称、角色形象、纹样或资产；题材（希腊神话）属公共领域，形象为本仓库原创 / 程序化生成。

### A.4 风格延续性论证（评审会第一问）

从 16×16 像素风过渡到 128 基准 HD，如何保持「同一个游戏」的观感？逐项锚定：

| 延续维度 | 现状（16×16 Kenney） | HD 目标 | 延续手段 |
|---|---|---|---|
| **色彩体系** | 灰砖墙（tint `0x9aa4b8`）、沙色地砖、暖灰/棕/青绿调 | 同色相族、扩展到 3–4 阶明度 ramp | 从现有调色板**采样色相与明度关系**，HD 只是把 2 阶压成 3–4 阶，不换色相 |
| **角色比例** | 头大身短的 chibi、深色描边 | 保持 ~1:1.6 头身比、保留柔化描边 | 沿用像素原型的**剪影外接框比例**（宽:高 ≈ 0.75），仅提升细节密度 |
| **剪影特征** | 史莱姆 / 骷髅 / 哥布林 / 红蟹 / 幽灵 | 团块 / 带角甲兵 / 瘦长突袭 / 球形引信 / 悬浮祭司 | **保留每个敌人的职能形态**，让老玩家凭轮廓认出「同一个怪」 |
| **可读性不变量** | 角色与地面高对比、深描边、朝向可读 | 同不变量 + 顶光方向统一（左上光源） | 明度阶梯（V3）是像素时代规则的显式化，不是新规则 |
| **屏幕体型** | 由 hurtbox 半径驱动缩放（`hurtboxSpriteScale`） | **不变**（仍由 hurtbox 驱动） | 分辨率提升 8× 但**屏幕占位不变**，玩法读数零变化（FR-008 机制复用） |
| **动作节奏** | 2 帧循环、130ms/帧 | 6–8 帧循环、83–125ms/帧 | 节奏「更快更顺」但不改变「循环 / 一次性」的语义（FR-006） |

**结论**：色相族、比例、职能形态、明度关系、屏幕体型五项全部延续；升级的是**细节密度与动作帧数**，不是身份。

## B. 逐资产规格（核心）

### B.0 全局约定

| 约定项 | 值 | 说明 |
|---|---|---|
| **统一基准像素** | **`tilePx = naturalPx = 128 × 128 px`** | 全项目**单一基准**（`data-model` VR-9）。= 1 世界单位 = 1 网格格（见 §C.1 论证）。`TILE_NATURAL_PX` 由 `16` 改为 **`128`**（`client/GameRenderer.ts`）。**回落档 = 64**（见 §C.1）。 |
| **`meta.tilePx`** | 每张图集 JSON 声明 **`meta.tilePx = 128`** | 工程侧**从纹理实际尺寸推导**缩放，不写死常量；`meta.tilePx` 是唯一权威来源 |
| **图集目录与命名** | `assets/art/hd/`；`player-hd` · `enemy-{grunt,elite,raider,bomber,gunner,unknown}-hd`（各一张）· `tiles-hd` · `fx-hd`（+ 必要时 `fx-font-hd`） | 每张 `X.png` + 同名 `X.json`。图集总数 **≤ 12**（见 §C.3） |
| **图集 JSON schema** | 沿用既有：`frames`（键 `<anim>.<n>`）、`animations`（键 `<spriteId>.<action>.<facing>`）、`meta{scale,size,tilePx}` | 命名契约**逐字不改**；回退链 `exact → action.down → idle.down` 保留 |
| **锚点（pivot）** | 角色 / 敌人 / 掉落物 = **(0.5, 0.5)** 画布中心；tile / 墙 = **(0, 0)** 左上；特效 = 按 §B.4 表 | 与既有 `AnimatedSprite.anchor === (0.5,0.5)` 断言一致（`tests/render/player_art.test.ts`） |
| **朝向枚举** | `down` / `up` / `left` / `right`（`Facing4`，与 `sprite-map.ts` 一致） | 四向，无八向（避免作画量翻倍且与模拟层四向量化不符） |
| **动作枚举** | `idle` / `move` / `dash` / `attack` / `hit` / `death`（`AnimationState`，6 个） | **完整交叉**：玩家 = 4×6 = 24 键；敌人 = 4×6 = 24 键（其中 `dash` 可别名到 `move`） |
| **动画键命名** | `<spriteId>.<action>.<facing>`；帧名 `<动画键>.<n>` | **MUST 逐字保留**（既有测试用字面量钉死，如 `player.base.idle.right.0`、`enemy.raider.dash.right.0`） |
| **显示高度** | 由 **hurtbox 半径** 驱动（`hurtboxSpriteScale(radius, 128, 10)`），**非**手调常量 | 世界单位→屏幕像素：1 unit = 10 px（`PX_PER_UNIT`），M17 相机再乘 `z` |
| **色彩空间** | sRGB · RGBA8888 · 预乘透明按 PixiJS 默认 | — |
| **描边** | 角色 / 敌人 2–3 px 柔化深色描边（比环境暗 30% 明度） | 保证任何地面上都分离 |

#### B.0.1 碰撞体锚定与比例（FR-008 / SC-004 硬约束）

- 渲染器既有锚点 `anchor = (0.5, 0.5)`（画布中心），由 `tests/render/player_art.test.ts` 钉死 → **本规格沿用，不新增锚点概念**。
- `hurtboxSpriteScale(radius, naturalPx, PX_PER_UNIT)` 把「单帧自然像素」映射到「hurtbox 直径」⇒ **帧外接框 ≡ hurtbox 直径**（1 世界单位 = 128px 自然 = 屏幕上 `radius × 2 × 10` px）。
- **因此角色 / 敌人的视觉外接尺寸 MUST == 帧外接尺寸 == hurtbox 直径**（主体填满帧安全区，内边距 ≤ 8px）。采用**紧凑比例**（延续 16×16 时代的 chibi 头身比，见 §A.4），**头部不超出帧**，碰撞圆心 = 画布中心。
- **脚部接地线** = y ≈ 0.75·H（96/128），仅供绘制与墙脚阴影锚定，**不是** Sprite 锚点。
- 若未来要「高于碰撞体」的写实比例，MUST 新增独立字段 `groundAnchorY` 并在本规格**显式登记**（当前**不做**）。

### B.1 玩家（`player.base`）

- **画布**：**128 × 128 px**（人体占中央约 48 × 72 px，脚接地约 y=96，头顶约 y=24）
- **锚点**：`(0.5, 0.5)`；**朝向数**：4
- **动作 × 帧数 × 帧率**：

| 动作 | 每朝向帧数 | 循环 | 帧率 | `frameMs` | 相位说明 |
|---|---|---|---|---|---|
| `idle` | **6** | ✅ 循环 | 8 fps | 125 | 呼吸 + 披风微摆；首尾帧无缝（帧 5 与帧 0 姿态差 ≤ 2px） |
| `move` | **8** | ✅ 循环 | 12 fps | 83 | 标准行走循环（接触→下沉→通过→上升 ×2 步） |
| `dash` | **6** | ❌ 一次性（持末帧） | 15 fps | 67 | 起冲前倾 → 拖影拉伸 → 收势 |
| `attack` | **6** | ❌ 一次性（持末帧） | 18 fps | 56 | **起手 f0–f1 / 命中 f2–f3 / 收招 f4–f5**（见 §B.1.1） |
| `hit` | **3** | ❌ 一次性（持末帧） | 12 fps | 83 | 后仰 → 受创定格 → 回位 |
| `death` | **8** | ❌ 一次性（持末帧） | 10 fps | 100 | 跪倒 → 侧倾 → 消散 |

- **每朝向帧数合计**：6+8+6+6+3+8 = **37**；**全角色帧数** = 37 × 4 = **148 帧**。

#### B.1.1 attack 相位划分（供后续与模拟层攻击时序对齐）

`attack` 6 帧按**三相位**划分，供模拟层「起手—命中—收招」窗口对齐：

| 相位 | 帧 | 视觉事件 | 对齐目标 |
|---|---|---|---|
| **起手 windup** | f0–f1 | 抬手 / 后拉蓄力，重心后移 | 模拟层攻击前摇（无判定） |
| **命中 active** | f2–f3 | 挥击过顶 / 前刺，**f3 为接触顶点**，附带 1 帧武器拖影 | 模拟层 hitbox 生效窗口 |
| **收招 recovery** | f4–f5 | 收势回位，重心前移归位 | 模拟层后摇（无判定） |

> **对齐口径（诚实披露）**：渲染动画由**真实帧时钟**（`ticker.deltaMS`）驱动，**不**由逻辑 tick 驱动（ADR-002，`tests/render/player_art.test.ts` 已钉）。因此三相位与模拟层窗口的对齐是**视觉最佳努力**，权威时长仍是模拟层 `ATTACKING` 状态的持续 tick 数。规格**不新增**任何模拟层状态或字段（FR-003）。

#### B.3.2 墙体拆解：顶面 cap / 立面 face / 墙脚阴影

**关键设计决策（回答 FR-008 / FR-010 的核心）**：墙体**不做任何像素外溢**。每个墙格 128×128 的贴图内部，纵向分为三带：

```
墙格 128×128（世界 1×1，= 碰撞 AABB 的一格）
┌───────────────────────────────┐  y=0     ← 墙格顶边 = 碰撞顶边
│  ┌─────────────────────────┐  │
│  │   ① 顶面 cap（顶视石材）  │  │  占上 ~55%（y=0 … y=70）
│  │   高光在上缘，表示受光顶面 │  │
│  └─────────────────────────┘  │  y=70    ← cap/face 交界（一条砖缝线）
│   ② 立面 face（竖向砖纹）      │  │  占下 ~45%（y=70 … y=124）
│   底缘压暗，表示立面背光        │  │
│ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓  │  y=124   ← ③ 墙脚阴影（y=124…128）
└───────────────────────────────┘  y=128   ← 墙格底边 = 碰撞底边
```

| 带 | 纵向范围（128 基准） | 作用 | 光照规则 |
|---|---|---|---|
| ① 顶面 cap | y = 0 … 70（~55%） | 表示墙的**水平顶面**，读作「墙有多厚」 | 上缘 + 左缘提亮（左上光源，V5） |
| ② 立面 face | y = 70 … 124（~43%） | 表示墙的**竖直表面**，读作「墙有多高」 | 底缘压暗，中段横向砖缝 |
| ③ 墙脚阴影 | y = 124 … 128（~2%，即 4px） | 让墙「坐」在地面上，锚定接触 | 低 alpha 黑，**仍在墙格内** |

> **为什么这样不会造成视觉 / 碰撞偏差（SC-004）**：
> 碰撞几何 = 墙格自身 1×1 的 AABB。上述三带**全部位于该 1×1 像素范围内**，因此墙体的**可见外接框**与**碰撞外接框**逐格重合，**偏差 = 0**。玩家从任何方向贴墙，被阻挡的位置都恰是贴图的边缘。
>
> **为什么不采用「立面朝屏幕内侧延伸（向下外溢）」的方案**：若立面越过墙格底边继续向下延伸，则墙体**可见底边**位于碰撞底边之下；玩家从下方（南）靠近时会在碰撞底边（墙格底边）被挡住，却视觉上「站进了立面里」—— 这正是 FR-008 禁止的偏差；且立面会覆盖下方**可通行地面**，违反 FR-010。故**明确否决外溢方案**，改用「格内三带分层」。
>
> **FR-010 保证**：因为立面**不越过墙格底边**，其下方（南侧）的可通行地面**永不被覆盖**；顶面覆盖墙格自身（本就是不可通行的墙），也不影响任何可通行地面。可通行区域始终清晰可辨。

**`depthExtentPx`（可选增强，基线 = 0）**：为使厚墙更有「高墙」体量感，允许立面**向相邻墙格**延伸 `depthExtentPx`（**仅当相邻格也是墙**时）。规则与工程侧一致（`data-model` E3 / `engineering-architecture.md`）：

| 相邻格状态 | 立面行为 |
|---|---|
| 相邻格**可通行** | 立面**必须收在墙格内**（`depthExtentPx = 0` 于该侧） |
| 相邻格**也是墙** | **可**向该墙格延伸 `depthExtentPx`（基线 0，增强档 **≤ 64px**，即 ≤ 0.5 格） |

- **基线交付取 `depthExtentPx = 0`**（零外溢，逐格 1 Sprite，节点结构零改动，SC-004 偏差 = 0，FR-010 平凡成立）。
- 增强档的延伸**只进入墙格**（永不进入可通行格），且墙体位于 `staticLayer`（camera index 0，实体之下），因此**既不覆盖可通行地面，也不遮挡角色**（FR-010 仍成立）。

#### B.3.3 autotile / 位掩码规则（如何自动选对部件）

**输入**：由 `world.query(WallComponent)` 得到的**全部墙实体**（只读）。因 `LevelLoader` 把 `1` 格**合并成大矩形**，渲染层 MUST 先把矩形展开为**墙格占用集** `occupied(c, r)`（整数格，确定性、行主序），再逐格算掩码。

**邻接掩码**（8 邻，bit 值如下；`occupied` 为真则置位）：

| bit | 邻居 | 值 | bit | 邻居 | 值 |
|---|---|---|---|---|---|
| 0 | N (c, r−1) | 1 | 4 | NE (c+1, r−1) | 16 |
| 1 | E (c+1, r) | 2 | 5 | SE (c+1, r+1) | 32 |
| 2 | S (c, r+1) | 4 | 6 | SW (c−1, r+1) | 64 |
| 3 | W (c−1, r) | 8 | 7 | NW (c−1, r−1) | 128 |

**部件选择**：`mask` → 47 部件之一的查表（标准 blob autotile）。**4 邻位**决定直段 / 端点 / 转角 / T 形，**4 角位**决定**内侧角（concave corner）**的补角部件。

4 邻位核心 16 例的部件角色（bit 置位 = 该侧是墙）：

| N | E | S | W | mask | 部件角色 | 顶面边缘处理 |
|:-:|:-:|:-:|:-:|:-:|---|---|
| 0 | 0 | 0 | 0 | 0 | **孤立单格** | 四面都有 rim |
| 1 | 0 | 0 | 0 | 1 | 竖直端点（下） | 左/右/下 rim，上无缝 |
| 0 | 0 | 1 | 0 | 4 | 竖直端点（上） | 左/右/上 rim，下无缝 |
| 1 | 0 | 1 | 0 | 5 | 竖直直段 | 左/右 rim |
| 0 | 1 | 0 | 0 | 2 | 水平端点（左） | 上/下/右 rim，左无缝 |
| 0 | 1 | 0 | 1 | 10 | 水平直段 | 上/下 rim |
| 0 | 1 | 1 | 0 | 6 | 转角（左上内角） | 上/左 rim |
| 1 | 1 | 0 | 0 | 3 | 转角（右下内角） | 下/右 rim |
| 1 | 1 | 1 | 0 | 7 | T 形（缺右） | 右 rim |
| 1 | 1 | 1 | 1 | 15 | **内部满格** | 无 rim（无缝延伸） |

（其余组合同理由 4 邻位决定；4 角位仅在内侧角处叠加补角部件，用于「凹角」处的过渡砖。）

**确定性与完备性**：
- 变体选择 MUST 是 `(c, r, mask)` 的**纯函数**，MUST NOT 随机（`data-model.md` VR-13）。
- 掩码空间 MUST **完备覆盖**：任一 mask 都有对应部件；未显式列出的组合 MUST 落到**兜底部件**（`tile.wall.15`，即内部满格），保证不出现空洞。
- 地面变体选择同样 MUST 确定性（按 `hash(c, r) % 4`），避免同屏重复感而不引入随机。

**与既有节点结构兼容（重要）**：
- **每个墙格 = 恰好 1 个 `Sprite`**（贴图自身已合成 cap + face + 阴影三带）。因此既有断言 `wallNode.children.length === round(w) × round(h)`（`tests/render/tilemap_art.test.ts`）**无需修改即继续成立**，且一个墙实体仍对应**一个节点**（`staticLayer.children[i+1].x === wall.x * PX_PER_UNIT` 不变）。
- 掩码跨墙实体计算（相邻格可能属于不同合并矩形），渲染层用**全量墙格集**计算，只读、无写回（宪法 Principle V）。
- 每格 1 Sprite 亦保证 `SC-010` 的逐帧开销比值可控（30×30 房最多 ~900 格，一次性铺设、签名守卫，非逐帧重建）。

#### B.3.4 墙体不遮挡可通行地面（FR-010）

三条保证，全部来自「格内三带」设计：
1. 立面**不越过**墙格底边 → 南侧可通行格不被覆盖。
2. 顶面只覆盖**墙格自身**（不可通行）→ 不涉及可通行地面。
3. 墙脚阴影**封顶 4px 且低 alpha**，且**仍在墙格内** → 即便邻格是地面，也只是墙格边缘的暗边，不侵入地面格。

## C. 分辨率与体积预算（规划硬输入）

### C.1 基准 tile 像素尺寸：**128 × 128**（理由）

**约束链**：世界单位→像素 `PX_PER_UNIT = 10`；M17 相机缩放 `z` 由房间与视口决定（`ZOOM_FIT_MARGIN = 0.8`，`ZOOM_MIN=1`，`ZOOM_MAX=16`）。房间短边恒占视口短边 80%（`specs/025`）。

| 场景 | 房间 | `z` | 1 格屏幕尺寸（CSS px） | @DPR 1 | @DPR 2 |
|---|---|---|---|---|---|
| 1920×1080 | 10×10 起始房 | 8.64 | 86.4 | 86 px | 173 px |
| 2560×1440 | 10×10 | 11.52 | 115.2 | 115 px | 230 px |
| 1920×1080 | 30×30 压测房 | 2.88 | 28.8 | 29 px | 58 px |
| 任意 | 3×3 极小房（夹到 `z=16`） | 16 | 160 | 160 px | 320 px |

**判定**（对照 FR-025 / SC-009「100%–400% 显示倍率下清晰、无像素块放大、无可见锯齿」）：

| 候选 | 覆盖情况 | 体积影响 | 结论 |
|---|---|---|---|
| 64 × 64 | 起始房 @DPR1 已 86px > 64 → 1.35× 放大，@DPR2 2.7× 放大 | 最小 | ❌ 偏软 |
| **128 × 128** | 起始房 @DPR1 **86 < 128**（缩小，最锐）；@DPR2 173px → 1.35× 放大（远 < 400% 容差）；`z=16` @DPR2 320px → 2.5×（仍 < 400%） | 适中 | ✅ **选定** |
| 256 × 256 | 全场景 pixel-perfect | ≈ 4× | ⚠️ 预算吃紧，列为可选「最高保真」档 |

> **选 128 的结论**：在**全部现实场景**（含 DPR2、含 `z=16` 极端小房）下，放大倍率均 ≤ 2.5×，落在 SC-009 的 400% 容差内；同时体积可控。`TILE_NATURAL_PX` 由 `16` 改为 `128`，贴图按 `PX_PER_UNIT / TILE_NATURAL_PX = 10/128` 缩放 → 1 格恒为 1 世界单位，**FR-009「按房间实际尺寸铺展、不拉伸」成立**。

> **回落档 = 64（若环境重绘不在预算内）**：环境源包 S1 原生为 **64×64**。若无力把环境重绘到 128，则**全项目统一回落 64**（`tilePx = naturalPx = 64`，单一基准仍满足 VR-9）。此时起始房 @DPR1 = 1.35× 放大、@DPR2 = 2.7× 放大，**仍在 SC-009 的 400% 容差内**（`linear` + mipmap 下无锯齿 / 无摩尔纹），但锐度低于 128。**触发条件**：环境重绘工期不可得。**默认仍取 128**（本特性主题即「高清」）。

### C.3 建议的新体积预算

| 项 | 旧值（像素时代） | **新值（HD，已与工程侧对齐）** | 依据 |
|---|---|---|---|
| **单文件上限** | < 1 MB | **≤ 4 MiB** | 最大单张 `player-hd` @0.75 ≈ 1.82 MB、`enemy-elite-hd` ≈ 1.77 MB，留 ~2× 余量 |
| **资产总量上限** | < 6 MB | **≤ 32 MiB** | 全量 @0.75 ≈ **9.64 MB**，余量充裕（防未来增补） |
| **单图集像素上限** | （无） | **≤ 4096 × 4096**（目标 ≤ 2048×2048） | WebGL `MAX_TEXTURE_SIZE` 下限保证 + 低端余量 |
| **图集数量上限** | （无） | **≤ 12 张**（当前 10 张） | 替代旧断言的强度，防止「放宽单文件上限 ⇒ 无上限」（VR-24） |

- **数值口径**：以上为**工程侧提议值**，与 `engineering-architecture.md` §6 一致；本规格的 128 基准方案在全部四项内**均有余量**，故**无需工程侧调整预算或切分**。
- 更新落点：`tests/assets/licenses.test.ts` 的体积断言（旧 `1MB / 6MB`）→ 新 `4MiB / 32MiB` + **新增图集像素上限（4096²）与图集数量（≤12）断言**（`contracts/hd-asset-manifest.md` §6 已授权；FR-029 已授权更新该套件）。
- **强度不可退化**：放宽单文件上限时 MUST 同时新增**图集像素尺寸上限**与**图集数量上限**两条等价强度约束（VR-24）。

**显存提示**：12.85 Mpx RGBA8888 ≈ **51 MB** 显存（含 mipmap ≈ 68 MB）。六类敌人共享图集（按 `source` 去重），故 150 敌人同屏时**显存不随实体数增长**；仅需确认 SC-010 的**逐帧 CPU 耗时比值 ≤ 1.2**（贴图内存属 GPU 侧）。

### C.4 纹理过滤策略（直接影响 FR-025）

**背景**：M17 为实现像素锐利，把 `TextureSource.defaultOptions.scaleMode` 全局设为 `'nearest'`，并由 `tests/render/camera_zoom_sharpness.test.ts` 以**字面量 `'nearest'`** 钉死。该测试**不在**本特性授权的 `tests/render/*_art` 集合内。

**建议：按资产分别设置（推荐方案 (a)）—— 全局默认保持 `'nearest'`，HD 世界美术纹理显式覆盖为 `'linear'` + 开启 mipmap。**

| 资产类别 | `scaleMode` | `autoGenerateMipmaps` | 理由 |
|---|---|---|---|
| HD 世界美术（角色 / 敌人 / 地面 / 墙 / 特效 / 掉落物） | **`'linear'`** | **`true`** | HD 手绘**不是**像素画；`z=8.64`、DPR=1.5/2 等**非整数倍**放大下，`nearest` 会产生硬锯齿与闪烁。`linear` 平滑放大、`mipmap` 消除**缩小**时的摩尔纹（30×30 房 `z=2.88`、DPR1 时 128px→29px，缩小 4.4×，**无 mipmap 必现摩尔纹**，违反 SC-009）。 |
| 保留的像素风 UI（若仍有） | `'nearest'` | `false` | 保持像素锐利（本特性不改 UI，仅说明策略可分资产） |

**为何不全局改 `'linear'`**：全局改会打破 `camera_zoom_sharpness.test.ts` 的冻结断言（该测试不在授权更新集内）。**按纹理覆盖**既满足 FR-025，又让 M17 测试**零改动**继续通过 —— 与 `plan.md` Complexity Tracking 的推荐路径一致。

**实现要点**：`TextureSource.defaultOptions.scaleMode` 在 `AssetCatalog.load()` 开头仍设 `'nearest'`（M17 断言保留）；随后对**每个 HD 世界美术的 `TextureSource`** 显式设 `source.scaleMode = 'linear'` 且 `source.autoGenerateMipmaps = true`。UI 纹理不受影响。

**图集 padding**：mipmap 会在低 mip 层级跨帧取样，故图集内相邻帧之间 MUST 留 **≥ 4px 透明 gutter**（2048² 图集尤其重要），否则低 mip 会出现帧间渗色。

### D.2 开放许可素材**覆盖不到**的部分（缺口诚实披露）

| 缺口 | 严重度 | 现实情况 | 补齐方案 |
|---|---|---|---|
| **4 向 × 6 动作的高清玩家角色** | **高** | CC0 库中「4/8 向 + 行走」有（S5/S6），但**攻击 / 受击 / 死亡相位**几乎不存在 | **本仓库原创绘制 + 程序化派生**：以 CC0 基底（S5/S6）的 idle/move 为锚，attack/hit/death 由**本仓库原创关键姿态**绘制或**程序化变换**生成（squash / 前倾 / 拖影 / 消散）。程序化变换为本仓库原创，许可安全 |
| **5 类差异化敌人 × 4 向 × 6 动作** | **高** | CC0 怪物多为**单帧或单朝向**静态图 | 同上：以 CC0 怪物基底（S3/S1）为形，**本仓库重绘 HD 四向**；差异化靠 §B.2.1 形态语言（原创） |
| **带深度 / 透视的 HD 墙体 + 完整 autotile** | **低** | **S1 覆盖良好**（64px、完整 autotile、CC0） | **采用 S1**；若需 128 基准，则**本仓库按 S1 版式重绘至 128**（CC0 允许衍生，登记 modifications）；否则**回落 64 基准 tile（仅地面 / 墙）** |
| **HD 伤害数字 / 掉落物** | **低** | 零散可得 | 本仓库原创字形与图标（沿用「实心 = 拾取 / 空心 = 躲避」形状语言） |

**补齐总策略（混合三源）**：
1. **环境（墙 / 地面）**：**采用 S1（CC0，64px）**；按需本仓库重绘至 128（登记修改）。
2. **角色 / 敌人基底**：采用 **S5/S6（CC0）** 的形态与朝向，**本仓库 HD 重绘**其余动作。
3. **特效 / 掉落物 / 字形**：**本仓库原创 / 程序化生成**。

> **程序化生成的许可优势**：从单张高清概念图程序化派生朝向与动作，其**派生结果属本仓库原创变换**（与现行 `build-atlas.py` 的做法同源，只是 HD 化）。许可上安全、可登记为「本仓库原创 · 程序化派生」。

### D.3 许可口径建议

| 项 | 现状 | **建议** |
|---|---|---|
| `tests/assets/manifest.test.ts` 的「`license` MUST 恰为 `CC0-1.0`」 | 钉死单一许可 | **放宽为「命中经登记的开放许可白名单」**，白名单以**显式字面量列表**声明（禁止空真断言） |
| 白名单内容 | `['CC0-1.0','public-domain']` | **`['CC0-1.0','public-domain','CC-BY-4.0','CC-BY-SA-4.0']`**（与工程侧一致）；**ShareAlike 义务 MUST 在 `LICENSES.md` 逐条注明** |

**美术总监口径（专业建议）**：白名单按工程侧为 **`CC0-1.0 / public-domain / CC-BY-4.0 / CC-BY-SA-4.0`** 四档。但**选材默认优先 CC0 / 公共领域 / CC-BY（无传染）**；**ShareAlike（CC-BY-SA）作为白名单成员允许使用，但默认不选** —— 它会对分发物施加义务。仅在**某个必需资产只能以 CC-BY-SA 获取**时才启用，并在 `LICENSES.md` 逐条注明义务。**GPL / 未知许可一律排除**（如 DCSS 的 unknown-license 子集、LPC 的 GPL 分支）。

### E.1 美术层面风险与缓解

| # | 风险 | 影响 | 缓解方向 |
