# Feature Specification: 相机缩放与视口自适应（M17）

**Feature Branch**: `025-camera-zoom-viewport`

**Created**: 2026-10-02

**Status**: Draft

**Input**: User description: "解决高分辨率屏幕下游戏房间显示过小的问题（M17）。在表现层（client/）实现全局相机缩放（Camera Zoom）与视口自适应机制，使逻辑空间的网格在屏幕上按合理的比例放大显示（例如让 10x10 的房间能在屏幕居中且清晰可见）。要求：1. 游戏世界画面需等比放大，但静态 UI（如金币、血条HUD）需保持在屏幕边缘且不被模糊拉伸；2. 缩放必须是纯粹的渲染层视觉映射，绝对禁止修改逻辑层（src/）的碰撞箱尺寸、移动速度或任何物理参数；3. 原有 803 个测试用例必须保持 100% 绿灯。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 房间与角色在高分辨率屏幕上按合理比例放大 (Priority: P1)

玩家在 1920×1080 或更高的屏幕上打开游戏时，房间不再缩在画布一角、小到看不清，而是按一个舒适的比例铺满视野中央：起始房间（10×10 网格）完整可见、居中，玩家与敌人都足够大，能一眼看清朝向、动作与彼此的距离。

**Why this priority**: 这正是本特性要解决的原始问题。当前世界以固定比例映射到屏幕（1 世界单位 = 10 屏幕像素），一间 10×10 的房间只占 100×100 像素——在 1920×1080 上不足屏面积的 0.5%，动作游戏所需的「距离感」与「可读性」完全丧失。它是其余所有故事的前提：不解决它，后面每一条都是在放大一个看不清的画面。

**Independent Test**: 只实现本故事即可交付：在 1920×1080 视口下加载起始房间，确认房间完整可见、居中，且其短边占据视口短边的一个可读比例；无需静态 UI 改动或窗口缩放逻辑即可完整验证。

**Acceptance Scenarios**:

1. **Given** 视口为 1920×1080，**When** 起始房间（10×10）加载完成，**Then** 房间的可见范围完整落在视口内，且其短边占据视口短边的比例落在可读区间（不小于 55%），不出现裁剪或溢出。
2. **Given** 任意一间房间加载完成，**When** 观察画面，**Then** 地板、墙体、玩家、敌人、投射物与特效均以同一倍率放大，彼此相对位置与尺寸关系不变形。
3. **Given** 玩家在房间内移动，**When** 位置改变，**Then** 房间在屏幕上保持居中且**静止**（房间模式），玩家相对房间的位移直接体现为屏幕上的位移，房间边缘不出现裁剪、溢出或漂移。
4. **Given** 一间大到无法被完整容纳的房间，**When** 玩家移动到房间边缘，**Then** 相机以玩家为中心跟随并被钳制在房间边界内，房间之外的内容不进入视口，画面仍可读、不出现荒谬的过度缩小或放大。

---

### User Story 2 - 静态界面保持在屏幕边缘且不被模糊拉伸 (Priority: P1)

金币读数、生命/血条 HUD、奖励三选一菜单，以及死亡、胜利、营地覆盖层，始终贴在屏幕的固定位置，字号与图标尺寸与缩放前完全一致、边缘锐利。世界无论被放大到多少倍，界面都不会跟着一起被拉伸或糊掉。

**Why this priority**: 与故事 1 同级——用户把「世界放大」和「界面不变」作为同一句要求提出。二者缺一，结果都不可用：只放大世界而不固定界面，HUD 会随缩放漂移出屏幕或被拉成马赛克；只固定界面而不放大世界，则问题根本没解决。

**Independent Test**: 只实现本故事即可交付：把世界缩放设到多个不同倍率，逐一切换，确认 HUD 与各覆盖层的屏幕位置、尺寸与文字清晰度在所有倍率下完全一致。

**Acceptance Scenarios**:

1. **Given** 世界缩放处于任意倍率，**When** 玩家拾取金币或受到伤害，**Then** 金币读数与生命 HUD 的屏幕位置与尺寸与基线一致，文字保持清晰。
2. **Given** 世界缩放处于任意倍率，**When** 触发奖励三选一、死亡、胜利或营地界面，**Then** 这些覆盖层以屏幕空间呈现，不随世界缩放变化。
3. **Given** 世界被显著放大，**When** 观察 HUD 文字与图标，**Then** 不出现模糊、锯齿放大或非等比拉伸。

---

### User Story 3 - 视口尺寸变化时自动重新适配 (Priority: P2)

玩家调整窗口大小、切换全屏或在不同分辨率的屏幕上打开游戏时，画面自动重新适配：房间始终完整可见、比例依旧合理，无需手动操作或刷新页面。

**Why this priority**: 真实使用中分辨率千差万别，且窗口随时会变。它不改变核心体验，但决定特性在「非理想视口」下是否仍然成立。优先级低于前两者，因为它依赖前两者已成立。

**Independent Test**: 只实现本故事即可交付：在运行中连续改变视口尺寸（含极端的超宽与超高比例），确认画面每次都自动重新适配、房间保持完整可见。

**Acceptance Scenarios**:

1. **Given** 游戏正在运行，**When** 窗口尺寸改变，**Then** 画面在无需手动干预的情况下重新适配，房间仍完整可见且比例合理。
2. **Given** 一个极端宽高比的视口（超宽或超高），**When** 房间加载，**Then** 以受限方向为准完成适配，房间完整可见、不出现裁剪或溢出。
3. **Given** 视口在较小尺寸（如 800×600）与较大尺寸（如 3840×2160）之间变化，**When** 每次变化完成，**Then** 房间在两个极端下都清晰可读，且适配过程不出现可见的跳变或闪烁。

---

### User Story 4 - 缩放是纯表现层映射，玩法逐位不变 (Priority: P2)

无论画面被放大多少倍，游戏的玩法完全不变：角色的碰撞体积、移动速度、攻击距离、伤害判定都与改动前逐 Tick 一致。缩放只改变「看起来多大」，绝不改变「实际是什么」。

**Why this priority**: 这是本特性的安全底线，也是用户明确写下的硬约束。它不新增体验，但一旦被违反，整个项目的确定性保证与回归基线即刻作废。优先级置于 P2 是因为它必须由 P1 的存在才被触发。

**Independent Test**: 只实现本故事即可交付：在固定种子与固定输入序列下，分别以「不渲染」与「渲染（含缩放）」运行同一段模拟，比较两次产生的状态序列。

**Acceptance Scenarios**:

1. **Given** 相同的种子与相同的输入序列，**When** 分别在启用与不启用渲染缩放的条件下运行，**Then** 两次产生的模拟状态逐 Tick 完全一致（0 处差异）。
2. **Given** 缩放处于任意倍率，**When** 玩家贴墙移动或与敌人碰撞，**Then** 被阻挡的位置与判定范围与缩放倍率无关。
3. **Given** 缩放处于任意倍率，**When** 检查依赖方向，**Then** 不存在任何从模拟内核指向表现层的依赖。

---

### User Story 5 - 既有测试与场景图契约零回归 (Priority: P3)

本特性落地后，项目原有的 803 个测试用例全部保持通过，既有的渲染场景图冻结契约一条都不被破坏，新增能力以「默认恒等」的方式向后兼容。

**Why this priority**: 它是一条交付保障而非新体验。放在最后是因为它约束的是「怎么交付」而不是「交付什么」；但它必须在任何一次合入前成立。

**Independent Test**: 只实现本故事即可交付：在改动后运行完整测试套件，确认 803 个用例 100% 通过，且既有的相机跟随与场景图断言无需修改即继续成立。

**Acceptance Scenarios**:

1. **Given** 改动完成，**When** 运行完整测试套件，**Then** 原有 803 个用例 100% 通过，无失败、无新增跳过。
2. **Given** 在无法读取视口尺寸的降级环境下，**When** 运行既有的相机行为断言，**Then** 相机行为与改动前逐位一致，既有断言无需修改即成立。
3. **Given** 改动完成，**When** 检查渲染场景图，**Then** 全部既有冻结契约（相机为舞台唯一子节点、渲染根为相机最后子节点、特效层为渲染根最后子节点、静态层为相机索引 0、无墙时相机恰有 1 个子节点、空闲时特效层恰有 0 个子节点）均未被破坏。
4. **Given** 处于无墙场景或房间尚未加载（营地/枢纽、加载间隙），**When** 渲染进行，**Then** 缩放为恒等（1），相机行为与改动前逐位一致，且不抛错、不阻塞渲染。

---

### Edge Cases

- 当视口尺寸无法被读取时（降级环境），缩放如何取值？（必须退化为恒等，且相机行为与改动前逐位一致）
- 当视口尺寸可读但退化为 0 或负值（极小化窗口、隐藏容器）时，缩放是否同样退化为恒等，而不是产生除零、`NaN` 或无穷倍率？
- 当房间范围无法被确定时（无墙场景、房间尚未加载、营地/枢纽等非房间场景），缩放如何取值？（必须退化为恒等 1，且不抛错、不阻塞渲染）
- 当房间尺寸极小（如仅 3×3）时，缩放 MUST 被上限（`ZOOM_MAX = 16`）截断，MUST NOT 把一格放大到占满整屏；此时**允许**屏占比低于 SC-001 的 55% 下限（3×3 ⇒ `z` 夹到 16 ⇒ 房间占视口短边约 **44%**），SC-001 的 55%–85% 区间**只适用于 10×10 起始房间**。
- 当房间尺寸远大于视口（如 30×30 压测房）时，缩放是否被下限保护，避免实体小到无法辨认？
- 当视口宽高比极端（超宽或超高）时，如何决定以哪个方向为准适配，且保证房间完整可见？
- 当窗口在运行中被反复快速缩放时，是否出现画面抖动、撕裂或闪烁？
- 当玩家走到房间边缘时，是否仍保证房间完整可见（房间模式：房间静止不动、不漂移；跟随模式：相机钳制在边界内，房间之外不进入视口）？
- 当房间尺寸恰好落在「可容纳 / 不可容纳」的临界点上时，取景模式的判定是否稳定、不出现逐帧抖动？
- 当视口缩小到使原本可容纳的房间变为不可容纳（或反之）时，取景模式切换是否可预测、不出现肉眼可辨的跳变？
- 当设备像素比很高（高 DPI 屏）时，世界内容放大后是否保持清晰、不糊？
- 当世界内容被显著放大时，像素美术是否出现渗色或采样模糊？
- 当相机缩放与既有的屏幕震动叠加时，是否出现互相干扰或使缩放产生漂移？
- 当从菜单/覆盖层回到游戏时，缩放是否正确恢复，不出现残留的错误倍率？
- 当同一帧内既发生视口变化又发生相机跟随更新时，缩放与跟随的应用顺序是否稳定、可预测？
- 当 `zoomActive === false` 时，行为是否与改动前**逐位一致**（不引入哪怕一像素的偏移）？—— 逐位等价的**唯一前提是谓词** `zoomActive === false`（即「视口不可读 ∨ 房间范围不可确定」），**不是** `z` 的取值。特别地，`zoomActive === true ∧ z === 1`（房间大到 `fitZoom ≤ 1.25`，正是 US1 场景 4 的情形）时，房间模式与跟随模式**有意**偏离旧公式（房间居中 / 边界钳制正是本特性的目的），此时 MUST NOT 要求逐位等价。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 表现层 MUST 提供一个全局、统一的相机缩放因子，作用于**全部世界空间内容**（地板、墙体、玩家、敌人、投射物、危险预警、掉落物、命中特效、伤害跳字）。
- **FR-002**: 缩放因子 MUST 由**当前房间的范围**与**当前视口的尺寸**共同决定，使房间在视口内以合理留白完整可见；MUST NOT 依赖针对某个房间尺寸的硬编码。
- **FR-003**: 缩放因子 MUST 被夹在「下限 / 上限」区间内，使极小房间不被放大到荒谬、极大房间不被缩小到不可辨认。
- **FR-004**: 相机取景 MUST 按「房间是否可被完整容纳」分为**两种且仅有两种**模式：
  - **房间模式（房间可被完整容纳）**：房间 MUST 居中于视口并保持**静止**（不随玩家移动而漂移）；玩家在房间内自由移动。这是全部常规房间（起始 / 竞技 / 压测房）的默认取景。
  - **跟随模式（房间大于视口）**：相机 MUST 保持既有的「以玩家为中心」跟随语义，且取景 MUST 被**钳制在房间边界内**——房间边缘之外 MUST NOT 进入视口。
  - 模式判定 MUST 只由「房间能否被完整容纳」决定，MUST NOT 依赖玩家位置或任何其它状态。
  - 两种模式都必须保证：房间可见范围 MUST 完整落在视口内，MUST NOT 出现裁剪或溢出。
- **FR-005**: 世界空间内容 MUST 等比缩放（横纵同倍率），MUST NOT 出现非等比拉伸。
- **FR-006**: 静态界面（金币读数、生命 HUD、奖励三选一菜单、死亡/胜利/营地覆盖层）MUST NOT 受世界缩放影响：其屏幕位置与视觉尺寸 MUST 与缩放引入前一致。
- **FR-007**: 静态界面的文字与图标 MUST 以原生清晰度呈现，MUST NOT 因世界缩放而模糊或拉伸。
- **FR-008**: 世界空间内容放大后 MUST 保持清晰；像素美术 MUST 采用保持锐利的采样方式，MUST NOT 出现肉眼可辨的模糊或渗色。
- **FR-009**: 在高设备像素比的屏幕上，画面 MUST 与设备像素比匹配呈现，MUST NOT 因缩放而变糊。
- **FR-010**: 视口尺寸发生变化（窗口缩放、分辨率切换、进入/退出全屏）时，缩放因子 MUST 自动重算并生效，MUST NOT 需要手动刷新或重新加载。
- **FR-011**: 在极端宽高比的视口下，系统 MUST 以受限方向为准完成适配，并保证房间完整可见、MUST NOT 出现裁剪或溢出。
- **FR-012**: 缩放 MUST 是纯表现层视觉映射：MUST NOT 修改模拟内核的碰撞箱尺寸、移动速度、攻击/伤害范围或任何物理与玩法参数。
- **FR-013**: 缩放 MUST NOT 改变模拟结果：在相同种子与相同输入序列下，模拟产生的状态序列 MUST 与改动前逐 Tick 一致。
- **FR-014**: 当视口尺寸**无法被读取、非有限或非正**时（降级路径），缩放因子 MUST 退化为恒等（1），且相机行为 MUST 与改动前逐位一致。
- **FR-015**: 相机缩放的引入 MUST NOT 破坏既有的渲染场景图冻结契约：相机恒为舞台的唯一子节点；渲染根恒为相机的最后一个子节点；特效层恒为渲染根的最后一个子节点；静态层（仅世界有墙时存在）恒为相机的索引 0；无墙时相机的子节点数恰为 1；空闲时特效层的子节点数恰为 0。
- **FR-016**: 表现层的改动 MUST NOT 引入任何从模拟内核指向表现层的依赖；依赖方向 MUST 保持单向。
- **FR-017**: 本特性 MUST 保持既有 803 个测试用例 100% 通过；MUST NOT 放宽、删除或改写任何既有断言以迁就新实现。
- **FR-018**: 在压测场景下，表现层引入缩放后的**每帧耗时** MUST NOT 相对基线出现实质增长；验收口径 MUST 为同机、同场景、同一脚本下的耗时**比值**（改动后 / 改动前 ≤ 1.2），MUST NOT 使用绝对墙钟阈值。
- **FR-019**: 相机缩放与既有的屏幕震动效果 MUST 互不干扰：震动不得使缩放产生漂移，缩放不得改变震动的衰减语义。
- **FR-020**: 缩放倍率的每一次变化 MUST 是确定性的——给定相同的房间范围与视口尺寸，MUST 得到相同的倍率，MUST NOT 依赖随机源或墙钟。
- **FR-021**: 当**房间范围无法被确定**时（无墙场景、房间尚未加载、营地/枢纽等非房间场景），缩放因子 MUST 退化为恒等（1），且此时 MUST 满足 `zoomActive === false`（这是「与改动前逐位一致」的**唯一前提**），相机与画面行为 MUST 与改动前逐位一致；退化 MUST NOT 抛错、MUST NOT 阻塞渲染。

### Key Entities *(include if feature involves data)*

- **视口（Viewport）**：可用绘制区域的尺寸；缩放适配的输入之一，随窗口尺寸与分辨率变化。
- **相机缩放因子（Camera Zoom Factor）**：作用于世界空间的统一缩放倍率；关键属性为「取值」「上下限夹取」「随视口/房间变化的重算时机」。
- **房间范围（Room Extent）**：当前房间的世界空间包围盒；缩放适配的另一输入，来自当前房间的网格尺寸而非硬编码；当它无法被确定时（无墙 / 房间未加载 / 营地等非房间场景），缩放退化为恒等。
- **世界空间内容 / 屏幕空间内容**：本特性引入的分类。前者随缩放变化（地板、墙体、角色、敌人、投射物、预警、掉落物、特效、跳字）；后者不随缩放变化（HUD、菜单、覆盖层）。
- **相机取景状态**：当前的取景模式（房间模式 / 跟随模式）与相应的相机平移目标。房间模式下相机静止、房间居中；跟随模式下保留既有的「以玩家为中心」平滑跟随并钳制在房间边界内。本特性在其上叠加缩放，不改变跟随的收敛语义。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在 1920×1080 视口下，10×10 起始房间完整可见、居中，其短边占据视口短边的比例落在 55%–85% 的可读区间内。
- **SC-002**: 在 1920×1080 与 2560×1440 两种分辨率下，观察者均判定「房间大小合适、内容清晰可读」，判定一致率 100%。
- **SC-003**: 在世界缩放取遍上下限之间的多个倍率时，HUD（金币、生命）与全部覆盖层的屏幕位置与视觉尺寸相对基线变化为 0，且文字无模糊。
- **SC-004**: 在固定种子与固定输入序列下，改动前后的模拟结果逐 Tick 完全一致（差异处数 = 0），证明玩法未被改变。
- **SC-005**: 视口在 800×600 至 3840×2160 之间连续变化时，房间始终完整可见（裁剪/溢出发生次数 = 0），且不出现肉眼可辨的跳变或闪烁。
- **SC-006**: 既有 803 个测试用例 100% 通过（失败 0、新增跳过 0），且既有相机跟随与场景图断言在未修改的前提下继续成立。
- **SC-007**: 在约 150 个敌人同屏的压测场景下，表现层**每帧耗时中位数**的「改动后 / 改动前」**比值 ≤ 1.2**（同机、同场景、连续 3 次取中位数）。判定 MUST 使用比值，MUST NOT 使用绝对墙钟阈值。
- **SC-008**: 在极端宽高比（如 32:9 与 9:16）的视口下，房间完整可见且内容可辨的通过率为 100%。
- **SC-009**: 相机缩放与屏幕震动同时生效时，观察者判定「两者互不干扰」的比例为 100%（无缩放漂移、无震动异常）。

## Assumptions

- 目标平台仍为桌面浏览器；本特性不引入新的玩法机制、不改动操作方式。
- 模拟内核被视为**冻结资产**：本特性只在表现层做视觉映射，不修改任何玩法规则、数值或物理参数（对应宪法 Principle I / II / VI）。
- **缩放策略取「按当前房间范围 + 视口尺寸自动适配，并夹在上下限之间」**，而非「固定的全局倍率」或「玩家手动调节」。理由：用户以「让 10×10 的房间能在屏幕居中且清晰可见」为例，指向的是与房间和视口相关的自动适配；固定倍率无法同时兼顾 10×10 与 30×30 两类房间。若后续需要手动缩放控制，另立增量。
- **相机取景分两种模式，且只由「房间能否被完整容纳」决定**（见 FR-004）：房间可容纳时**以房间为中心静态取景**（房间钉在屏幕中央、不随玩家漂移）；房间大于视口时才回到既有的「以玩家为中心」跟随并**钳制在房间边界内**。
  - 之所以**不是**纯玩家跟随：`FR-004` 若同时要求「以玩家为中心」与「房间完整可见且居中」，二者在数学上互斥——10×10 房间在 1080p 下，保证完整可见要求缩放 `z ≤ 5.68`，房间仅占视口短边 **52.6%**，低于 SC-001 的 55% 下限；且出生点在 `(4.5, 8.5)`（非房间中心）时纯跟随会立刻垂直溢出 194 px。
  - 之所以**不是**纯玩家跟随 + 钳制（保留跟随但永不裁剪）：1080p 下 10×10 房间仅占视口宽度 864/1920，水平富余 1056 px ⇒ 房间会随玩家左右滑动最多约 777 px，视觉上「房间在屏幕上飘」，与用户原话「让 10×10 的房间能在屏幕**居中**且清晰可见」相悖。
  - 房间模式是该判定的**默认结果**：全部现有房间（10×10 / 12×10 / 30×30）适配后均可被完整容纳，故常规玩法下相机静止、房间居中；跟随模式为防御性分支，仅在未来出现超大房间或极端小视口时生效。
- 静态界面当前是屏幕空间元素（DOM），天然不受世界缩放影响；本特性必须**保持**这一点，而不是把界面迁入世界空间。
- 世界单位到屏幕像素的既有换算关系（1 世界单位 = 10 像素）保持不变；缩放是叠加其上的**视口适配因子**，不替换该换算。
- 退化路径（视口尺寸不可读）下缩放恒为 1，行为与改动前逐位一致——这是既有渲染测试（使用不含屏幕尺寸的替身）能够**零改动**继续通过的前提。
- 既有 803 个测试用例**零改动**，既有渲染场景图的 6 条冻结契约不变。
- 性能验收沿用项目既有口径：同机、同场景、同脚本下的耗时**比值**（≤ 1.2），而非绝对墙钟阈值（宪法 Principle IV）。
- **对既有冻结项的显式授权**：`specs/19` §1.3 与 `specs/20` §2.1（I11）把相机显式冻结为「**只平移、不缩放**」。本规格是**唯一**授权改动该条目的治理文档：相机由「只平移」扩展为「平移 + 等比缩放」。扩展 MUST 严格保留 I11 的其余语义（实体/墙体视图仍持有世界坐标，只有相机节点承载视图变换）、I12（视口尺寸不可读时安全降级）、I13（场景图契约）、I14（相机为表现层独有、`src/` 无相机概念）。除此之外，本特性 MUST NOT 修改任何其它既有冻结项。
