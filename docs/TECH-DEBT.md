## TD-001 · M16 遗留死槽位

**现象**：`index.html` 声明了 `--ui-frame-slot` 与 `--ui-frame-slot-inlay`（默认 `none`），`client/assets/manifest.ts` 也注册了 `ui.frame.slot` / `ui.frame.slot-inlay` 并产出对应 PNG，但**全仓库没有任何 CSS 规则引用这两个变量**。

**证据**（全仓扫描无消费）：
```bash
grep -rn "var(--ui-frame-slot" --include="*.html" --include="*.css" --include="*.ts" . | grep -v node_modules
# 期望输出：仅 index.html 的 :root 声明行，无任何 var(...) 消费
```

**为何当时没发现**：M16 的断言只检查「槽位已声明且默认 `none`」，不检查「槽位被消费」。**「声明 + 注入 + 资产齐备 + 测试全绿」≠「被消费」**——M19 的 `--ui-frame-dash` 就是同一类缺陷，且对全部既有断言完全隐形。

**建议修复**：二选一——
1. 若确实需要：在对应表面补 `border-image-source: var(--ui-frame-slot)` 等消费；
2. 若已废弃：从 `index.html` 的 `:root`、`client/main.ts` 的 `applyUiSkin` 槽位表、`client/assets/manifest.ts` 中一并移除，并删除 `assets/art/ui/slot.png` / `slot-inlay.png`（注意 `ui_skin.test.ts` 断言「≥11 个 `none` 默认值」与 9 个槽位存在，需同步调整并显式登记）。

**已就位的守卫**：M19 新增的 `tests/ui/ui_degradation.test.ts`「**每个 M19 槽位都必须在样式表中被 `var(...)` 引用**」只覆盖 M19 的 7 个槽位，**尚未覆盖 M16 的既有 11 个**——修复 TD-001 时建议把该守卫**扩展到全部 `--ui-*` 槽位**，从机制上封死此类缺陷复发。

## TD-002 · 全局滚动条溢出（已排期）

**现象**：任何视口下，文档滚动高度恒为**视口高的 2 倍**，全屏游戏出现一条纵向滚动条。

**根因**：PixiJS 的 canvas 池在 DOM 中留下**第二个** `<canvas>`（**无 `id`、无 `class`、`position: static`**），其 `top` 恰为一个视口高，因此把文档流撑开一倍。渲染用的主 canvas 本身尺寸正确（`cssH` / `attrH` / `styleH` 均等于视口高）。

**证据（已 A/B 实测，非推断）**：`production/m18-baseline-scroll-ab.json`
```bash
# 在 M18 基线提交上跑与 M19 同一个探针
git worktree add .tmp/m18 8606ca5
cmd //c "mklink /J .tmp\m18\node_modules node_modules"
cd .tmp/m18 && npm run build
M19_OUT=<主仓>/production/m18-baseline-shots M19_SERVER_PORT=4174 M19_CDP_PORT=9336 \
  node <主仓>/production/m19-probe.mjs
```
结果：M18 基线 `8606ca5` 与 M19 工作树**同为 2× 滚动、同一溢出源元素**（5/5 视口）。M19 未改动 `html` / `body` / `#app` / `#app canvas` 任何规则，也未改动 `Application` / `canvas` / `mountCanvas` / `resizeTo` 任何一行。

⇒ **该缺陷早于 M16/M18 即存在，与 M19 无关**；M19 交付时刻意**未越界**去改全局 HTML 样式。

**建议修复**（一行）：
```css
html,
body {
  overflow: hidden;
}
```
放在 `index.html` 现有 `html, body { margin: 0; height: 100%; ... }` 规则内即可。修复后需复跑 `production/m19-probe.mjs`，把 `noScroll` 从「既有例外」恢复为**纳入 M19 判据**（探针中 `ok` 条件加回 `&& v.noScroll`）。

**归属**：下个迭代顺手加上（用户裁决 2026-10-03）。

## TD-003 · 绝对墙钟性能断言（主理人补录，待用户确认）

**现象**：`tests/performance/stress.test.ts` G2 断言 `ratio < 9`（50 敌人 vs 300 敌人的每 Tick 耗时比）。该比值本身是**缩放比**口径，但**基准量测为绝对墙钟**，机器负载一高就误报。阈值 9 与典型值 ~7.3 只差 23%，余量过窄。

**实测（2026-10-03 同机）**：

| 运行条件 | 结果 |
|---|---|
| 与全量套件并行（满载） | **失败**：`expected 9.173420085783121 to be less than 9` |
| 单独空载复跑（下午，机器空闲） | **5/5 通过**，`ratio = 6.82` |
| 单独复跑（晚间，机器较忙） | **失败**，`ratio = 9.59` / `10.08` |

**是否 M19 引入？——已 A/B 证伪（7 轮交替对照，`git worktree` 检出基线 `8606ca5`）**：

| 轮次 | M18 基线 | M19 工作树 |
|---|---|---|
| 1 | 7.38 | 7.39 |
| 2 | 7.07 | 7.20 |
| 3 | 7.50 | **9.42** |
| 4 | 7.70 | 7.28 |
| 5 | 7.23 | 7.27 |
| 6 | 6.35 | 8.45 |
| 7 | 7.70 | 7.58 |
| **均值** | **7.28** | **7.80** |

**7 轮中 5 轮两者几乎相同**（差 ≤0.13）；M19 侧偶发尖峰，M18 侧未出现 —— 但这是**环境噪声**，理由是不可反驳的结构性事实：

1. `git diff --stat 8606ca5 HEAD -- src/` **为空** ⇒ 两棵树被测的 `src/` **字节相同**；
2. 该测试的 import 面**只有** `../../src` 与 `vitest` ⇒ 它**无法观测** `client/` / `index.html` / `assets/` / `production/` 的任何变化；
3. 被测代码相同 ⇒ 比值差异只能来自环境（负载 / IO / 热节流）。M19 侧工作目录多了 `dist/` 与约 5 MB 证据产物，文件系统开销略高，与「偶发尖峰」一致。

**来源**：M15 引入（见 `production/m19-baseline.md` §1）。M19 未改动它。

**影响**：`npm test` 在 CI / 本地高负载下会偶发 1 例失败，容易被误判为真回归——M19 实施期间就实际发生了一次（工程侧「1126 通过 / 0 失败」与主理人首轮「1125 通过 / 1 失败」的唯一差异来源）。

**建议修复**：把基准量测也改为**同机同脚本的比值口径**（连续 N 次取中位数），或对该例引入「空载重试一次」的显式豁免并**在测试名与报告里写明**这是负载敏感项。**禁用**简单放宽阈值——那会把真正的二次复杂度回归一起放过去。

**备注**：本条由主理人在 M19 质量门中补录（详见 `production/m19-qa-report.md` §9 R4），**尚未经用户裁定**，仅登记。
